# Raw open questions from the analysis (pre-triage)

Consolidated verbatim from the per-section analysis notes.
Triage state lives in docs/open-questions.md; this file is the unfiltered feed.

- **[14-hugepages-and-system-tools.md]** Whether Blackhole has a channel-3 (or any 4th-channel) device-address-map carveout analogous to Wormhole's 768MB limit; the carveout is guarded specifically by ARCH::WORMHOLE_B0 and no Blackhole equivalent appears in these files.
- **[14-hugepages-and-system-tools.md]** Intended behavior of hugepages-override.txt when the total is not evenly divisible by device count (integer division silently drops the remainder and under-allocates).
- **[14-hugepages-and-system-tools.md]** Whether a Windows port must support Grayskull host memory at all (GS is 'P2P + 1 channel', EOL, and largely absent from newer UMD sysmem code).
- **[14-hugepages-and-system-tools.md]** Which IOMMU mode a given deployment actually runs in (passthrough hugepage path vs translating anonymous-mmap path) is not pinned down by these repos; the Windows DMA-remapping equivalent decision is not made for us.
- **[14-hugepages-and-system-tools.md]** Whether the Windows port must emulate both UMD hugepage codepaths (hugetlbfs-file path provisioned by the service, and anonymous MAP_HUGETLB fallback used on the IOMMU path) or can collapse to a single contiguous-allocation primitive.
- **[10-telemetry-hwmon.md]** Firmware value refresh cadence is invisible to the KMD: tag 5 UPDATE_TELEM_SPEED exists in the tag space (tt-umd telemetry.hpp:16) but is never read; the rate at which FW updates CSM values or increments TIMER_HEARTBEAT must come from firmware docs before adding any Windows-side caching
- **[10-telemetry-hwmon.md]** tt_aiclk/tt_axiclk/tt_arcclk units: driver prints the raw u32 with no conversion; conventionally MHz but neither documented nor enforced in the KMD (telemetry.c:35-47)
- **[10-telemetry-hwmon.md]** BH vs WH probe-time validation asymmetry: BH caches unvalidated tag addresses (read later fails -EINVAL), WH skips invalid entries at probe (attribute hidden); which behavior a port should normalize to is a policy choice with user-visible differences for malformed FW tables (blackhole.c:487-495 vs wormhole.c:574-577)
- **[10-telemetry-hwmon.md]** Stale CONFIG_HWMON=n stub in enumerate.c:78-82 stubs devm_hwmon_device_register_with_info but the driver calls the non-devm variant — apparent dead/broken code, not behavior to emulate
- **[10-telemetry-hwmon.md]** PCIe perf counter reads during an in-place reset (needs_hw_init true, BARs mapped) are permitted and return whatever hardware yields; whether that is meaningful is unspecified
- **[10-telemetry-hwmon.md]** hwmon channel visibility latches at registration time; a tag first published after a POST_RESET re-probe updates the cache but not hwmon visibility until re-registration — unclear if any tooling depends on late-appearing channels
- **[10-telemetry-hwmon.md]** Whether tt-smi/tt-flash parse exact formats (e.g. 16-hex-digit tt_serial, 4-part vs 3-part version strings) could not be confirmed from the provided repos (tt-umd and tt-system-tools contain no references to the tt_* sysfs names); treat formats as ABI regardless
- **[07-blackhole-hw.md]** BAR0 total size is never asserted; mapped offsets require >= 0x1FE00000 but what lies between 0x19400000 and 0x1FC00000 and above 0x1FE00000 is unknown from tt-kmd
- **[07-blackhole-hw.md]** BAR2 is mapped in full but only the iATU block at 0x1000 is touched; the rest of the BAR2 register map is undocumented in the driver
- **[07-blackhole-hw.md]** TLB fields stream_header and static_vc exist in the register layout but are never programmed; hardware semantics unknown
- **[07-blackhole-hw.md]** How the DWC interface-timer interrupt (config 0x930/0x934) is converted into an ASIC reset is CMFW behavior invisible to the driver, as is the required post-reset settle time for flag-4 resets on Blackhole
- **[07-blackhole-hw.md]** TRIGGER_RESET (0x56) payload values other than 3 (ASIC+M3) are undocumented in tt-kmd; source of truth is tt-zephyr-platforms.git
- **[07-blackhole-hw.md]** NOC_ID register at 0x1FD04044: only low 6 bits (x) are consumed and y=0 is assumed; full register format unknown
- **[07-blackhole-hw.md]** telemetry_probe validates base/data pointers with is_range_within_csm(addr, 1) rather than 4, allowing a base within 3 bytes of CSM end whose reads would exceed CSM - intentional slack or oversight?
- **[07-blackhole-hw.md]** Is the missing bar2_mapping NULL check in blackhole_init (blackhole.c:592) a bug or is BAR2 considered optional? Port must decide whether to treat map failure as fatal
- **[07-blackhole-hw.md]** Whether Galaxy Blackhole (subsystem 0x0047) needs personality-level differences beyond enumerate.c ordinal assignment is not visible in blackhole.c
- **[07-blackhole-hw.md]** Whether any board-type (p100/p150/p300) tuning matters to the KMD should be confirmed against tt-umd; the kernel driver itself has no board branches
- **[01-module-and-packaging.md]** Grayskull INF policy: Linux claims PCI DEV 0xFACA but probe returns -ENODEV; should the Windows INF bind-and-fail-start (mirroring Linux, blocking other drivers) or omit Grayskull entirely?
- **[01-module-and-packaging.md]** tools/current-version parses module.h while VERSION_UPDATE.md claims it extracts from dkms.conf - which file is authoritative when they diverge; the port needs an explicit single source of truth
- **[01-module-and-packaging.md]** Is runtime mutability of idle_power_down_grace_ms (sysfs 0644) a hard requirement, or is start-time registry configuration sufficient? No in-tree writer was found
- **[01-module-and-packaging.md]** udev MODE 0666 makes device nodes world-writable including reset and pin-pages ioctls - should the Windows SDDL replicate this permissive model or tighten it (UMD assumes unprivileged open works)
- **[01-module-and-packaging.md]** No consumer of /dev/tenstorrent/by-id/* symlinks was found in tt-umd - unknown whether external tooling (tt-smi etc.) relies on ASIC-ID-stable names, which decides if the Windows port needs an equivalent
- **[01-module-and-packaging.md]** modprobe.d-tenstorrent.conf documents only 4 of 6 parameters (missing power_policy, idle_power_down_grace_ms) and is excluded from release tarballs - intentional (internal-only params) or stale?
- **[01-module-and-packaging.md]** >32-device systems require raising max_devices at load; unknown whether any deployed configuration does this, i.e., whether the Windows port needs the knob at all
- **[01-module-and-packaging.md]** .shutdown aliased to .remove runs the full teardown at system shutdown - which subset (quiesce, watchdog reprogram, power state) firmware actually requires across warm reboot is not documented here and needs correlation with the enumerate/wormhole shutdown analysis
- **[09-arc-msgqueue.md]** Occupancy math (wptr-rptr)%(2*num_entries) in unsigned u32 is only correct across a pointer wrap when 2*num_entries divides 2^32, i.e. num_entries is a power of two; the driver reads num_entries from the QCB and never validates it. Is num_entries guaranteed by FW to be a power of two? If not, occupancy is miscomputed after wrap.
- **[09-arc-msgqueue.md]** send_arc_message takes no lock spanning the push/doorbell/pop transaction; the power-setting path is serialized by chardev_mutex while reset/init/cleanup are serialized by reset_rwsem (a different lock). Can a POWER_SETTING transaction interleave with a reset/init ARC transaction on the same device, breaking the single-outstanding-message assumption?
- **[09-arc-msgqueue.md]** Only bits 0-7 of queue_info (num_entries) are used; the meaning of the upper 24 bits (entry size? version? flags?) is unknown, and the driver hardcodes a 32-byte entry stride.
- **[09-arc-msgqueue.md]** Both wrappers treat response header==0 as success and any non-zero as failure, but the semantics of a non-zero response header (error code vs echoed opcode vs status bitfield) are not documented in these files, so callers cannot distinguish error causes.
- **[09-arc-msgqueue.md]** msgqueue.c relies solely on MMIO accessor ordering with no explicit barriers; the exact barrier placement a Windows KMDF port needs on non-x86/weakly-ordered targets (entry-writes before WPTR publish, WPTR publish before doorbell, RES_WPTR read before entry reads) is unverified.
- **[09-arc-msgqueue.md]** Doorbell semantics are inferred from comments only: whether the BH ARC_MSI_FIFO write and WH ARC_MISC_CNTL IRQ0 bit must strictly follow the WPTR store, and whether the WH IRQ0 bit auto-clears, is not confirmed against hardware documentation.
- **[03-chardev-and-fd-lifecycle.md]** tt_cdev_release_noc_cleanup gates only on detached, not reset_gen/needs_hw_init: a stale pre-reset fd closing mid-reset still performs its NOC write into possibly-in-reset hardware (chardev.c:869) - intentional or oversight?
- **[03-chardev-and-fd-lifecycle.md]** GET_HARVESTING (ioctl nr 1) has no handler and returns -EINVAL via fallthrough (chardev.c:631-632) - is the number reserved for legacy UMD probing, and must the Windows port reserve it?
- **[03-chardev-and-fd-lifecycle.md]** No compat_ioctl means 32-bit userspace is unsupported on Linux; should the Windows port reject or thunk WOW64 callers (struct layouts appear width-invariant but were not exhaustively verified)?
- **[03-chardev-and-fd-lifecycle.md]** open() never checks detached; a create racing device removal succeeds and then fails all operations - the equivalent KMDF create-during-surprise-removal behavior needs an explicit decision
- **[03-chardev-and-fd-lifecycle.md]** NOC cleanup coordinate bounds x,y <= 64 are marked TODO 'more robust validation' (chardev.c:467-469); may tighten upstream
- **[03-chardev-and-fd-lifecycle.md]** O_APPEND as the power-aware signal has no clean Windows CreateFile equivalent, and tt-umd notes O_APPEND 'temporarily disabled to investigate NOC1 issues' at one call site (tt-umd/device/pcie/pci_device.cpp:379) - replacement signal must be coordinated with the UMD Windows port
- **[02-enumeration-and-lifecycle.md]** chrdev region reserves only max_devices (32) minors but XArray ordinals can reach 2^31-1 with no clamp in devt_for_device — behavior with ordinal >= max_devices unverified (chardev.c:55, 85-88; enumerate.c:290-293)
- **[02-enumeration-and-lifecycle.md]** tenstorrent_register_device / cdev_device_add return value is ignored by probe (enumerate.c:375) — failure leaves a device with sysfs but no char device and remove calls cdev_device_del on a never-added cdev; intentional?
- **[02-enumeration-and-lifecycle.md]** kzalloc-failure path returns -ENOMEM without pci_disable_device, unlike the ordinal-failure path (enumerate.c:280-282 vs 295-299) — presumed leak/oversight
- **[02-enumeration-and-lifecycle.md]** stub IRQ handler returns IRQ_HANDLED unconditionally under IRQF_SHARED — on a shared INTx line it claims other devices' interrupts; unclear if future interrupt sources require status-register gating
- **[02-enumeration-and-lifecycle.md]** embedded struct device has release=NULL while memory is freed via a separate kref (chardev.c:103, enumerate.c:492) — relies on no outstanding kobject refs at kfree; runtime warning behavior unverified
- **[02-enumeration-and-lifecycle.md]** remove iterates open_fds_list and runs per-fd memory cleanup without chardev_mutex while opens are still possible (cdev not yet deleted) (enumerate.c:465-467) — potential race the port must resolve explicitly
- **[02-enumeration-and-lifecycle.md]** CONFIG_HWMON=n stub covers devm_hwmon_device_register_with_info but the code calls the non-devm variant (enumerate.c:78-82 vs wormhole.c:628/blackhole.c:664) — stub appears stale; hwmon-less build status unclear
- **[02-enumeration-and-lifecycle.md]** galaxy_bdf_to_ordinal ignores the PCI domain/segment (enumerate.c:51) — multi-segment Galaxy hosts could collide on fixed ordinals; is single-domain a real platform invariant?
- **[02-enumeration-and-lifecycle.md]** at remove/unload time cleanup_hardware is effectively skipped because both classes no-op when detached (already true) — firmware apparently stays in A0 after driver unload; intended?

- **[06-tlb-management.md]** Hardware TLB register state after ASIC reset is unobservable in the driver: registers are never cleared/reprogrammed on reset or free, so a port must not assume a benign default
- **[06-tlb-management.md]** Wormhole silently ignores tenstorrent_noc_tlb_config.static_vc (no register field) while Blackhole maps it to use_static_vc; unclear if WH hardware has an equivalent bit intentionally left unexposed
- **[06-tlb-management.md]** Semantics of ordering values other than 1 (documented only as 'strict') are defined by NOC hardware / tt-umd enums, not by tt-kmd; treat as opaque 2-bit passthrough
- **[06-tlb-management.md]** BAR mmap (RESOURCE0/2) exposes all TLB data windows and the TLB config register file without ownership checks, and tt-umd depends on it for userspace register writes; a Windows port must decide whether to reproduce this open-BAR model or force configuration through the ioctl
- **[06-tlb-management.md]** blackhole_init does not treat BAR2 iomap failure as fatal (blackhole.c:592 omits bar2_mapping), so later iATU writes could deref NULL; presumed latent bug, port should make it fatal
- **[06-tlb-management.md]** Whether the exact-size ALLOCATE_TLB contract (no round-up, tlb.c:24) is frozen uAPI behavior to copy verbatim on Windows
- **[06-tlb-management.md]** On BH with a small BAR4, describe_tlb still describes unallocatable 4G ids (uses compile-time total 210 while the allocator uses per-device counts); harmless today but an invariant to preserve when restructuring
